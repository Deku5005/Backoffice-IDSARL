📌 Contexte du scénario
Administrateur : admin@idsarl.com (Admin123!) – gère toute l'application.

Responsable finance : finance@idsarl.com (Finance123!) – gère les comptes et les mouvements.

Commercial : commercial@idsarl.com (Com123!) – gère les clients et les déploiements.

Développeur : dev@idsarl.com (Dev123!) – gère les produits, hébergements, réseaux sociaux et pages de contenu.

Consultation : consult@idsarl.com (Consult123!) – lecture seule du dashboard.

Étape 1 – L'administrateur se connecte
Endpoint : POST /api/auth/login

Requête :

json
{
  "email": "admin@idsarl.com",
  "motDePasse": "Admin123!"
}
Réponse (stockez accessToken pour la suite) :

json

  "accessToken": "eyJhbGciOiJIUzI1NiIs...",
  "refreshToken": "eyJhbGciOiJIUzI1NiIs...",
  "email": "admin@idsarl.com",

Étape 11 – Vérification du RBAC (accès refusés)
Avec un token COMMERCIAL, tentez GET /api/users → 403 Forbidden.

Avec un token DEVELOPPEUR, tentez POST /api/bank-accounts → 403.

Avec un token CONSULTATION, tentez POST /api/products → 403.

Seul l'ADMIN peut créer des utilisateurs. Seuls FINANCE et ADMIN peuvent gérer les comptes.

Étape 12 – Audit des opérations bancaires
Toute lecture ou modification des comptes/mouvements a automatiquement créé une entrée dans audit_logs.
Pour consulter ces logs, il faut un endpoint dédié (non fourni mais vous pouvez interroger la base directement).
Exemple de lignes d'audit générées :

CONSULTATION_COMPTE (lors des GET)

CREATION_COMPTE (lors des POST)

MODIFICATION_COMPTE (lors des PUT)

SUPPRESSION_COMPTE (lors des DELETE)
